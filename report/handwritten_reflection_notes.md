## Learning

- I learned how sequence-level knowledge distillation trains a small language model on the text
  generated by a larger teacher. The teacher API returns generated text rather than logits, so this
  project could not use logit-based distillation.
- I learned to divide teacher labeling across indexed Kubernetes workers, store data with an S3
  compatible service, clean and validate labels, and serve a model with a FastAPI service.
- I learned how Kubernetes readiness, rolling updates, recovery, resource limits, and an HPA affect
  a deployed service. I also learned that a network ACL is stateless and that rule order matters.
- I learned to use checksums and evaluation scores to record reproducible evidence, and to keep model
  weights out of Git and the container image.

## Challenges and solutions

- Teacher labeling takes time on CPU. I split the work into two indexed shards and added resumable
  worker behavior.
- Teacher labels can have invalid structure or slot values absent from the command. The cleaner
  counts each rejection category and removes duplicate commands before training.
- The student initially returned invalid output because the prompt's trailing space changed token
  boundaries. I aligned the prompt boundary in training, prediction, and serving; saved validation
  moved from 0% to 99% valid JSON.
- Model output must satisfy the response schema. The service validates its output and returns an
  error for invalid output instead of returning malformed JSON with a successful status.
- The network ACL needed explicit return-traffic rules. I checked the rule order with the supplied
  packet simulator and the sample passed 6/6 cases.

## Findings (saved measurements)

- Cleaning kept **2,861 of 3,000** commands. The saved counts balance: 0 invalid JSON, 1 wrong-key
  record, 3 invalid-intent records, 86 invented-slot records, and 49 duplicates were removed.
- Student v1 reached **99% JSON validity** and **43% full-frame accuracy** on 100 validation examples;
  the teacher reached 100% and 48%, respectively. Student v2 reached 97% and 44%.
- The saved cluster load run recorded **213 requests**, **2 failures**, **3,300 ms p95 latency**, and
  about **2.40 requests/second**. The three saved cold starts were **8 seconds** each.
- The saved rolling-update run had **2 failures out of 39 requests (5.13%)**, above the assignment's
  0.5% limit. This is a limitation to report accurately, not a passing result.
- The indicative cost calculation is an estimate: **0.91 INR per 1,000 requests** using the stated
  resource prices and measured throughput.
